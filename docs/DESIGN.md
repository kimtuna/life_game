# DESIGN.md — 무엇을 만드는가

> 이 문서는 초기 기획서입니다. 한 번 쓰고 나면 거의 고치지 않습니다.
> 방향이 바뀌면 여기를 고치고, 왜 바뀌었는지 한 줄 남겨두세요.
> **새로 열리는 세션이 이 프로젝트에 대해 아는 것은 이 md 파일들이 전부다.**
> 일부만 읽고 넘어가면 이미 있는 시스템을 다시 만들거나, 기존 설계와 어긋나게 구현할 위험이 크다.
> 이번 바퀴와 무관해 보이는 절이라도 전체를 다 읽는다.

## 무엇을

2D 탑다운 도트 그래픽 멀티플레이 게임. **힐링(생활: 채집/농사/목장)** 과 **PvP(총기 전투)**
두 축을 함께 가진다. 그래픽은 스타듀밸리 같은 도트 스타일. 전투 감각의 기준은 "덕코프".

(별도 언급 없음 — 필요해지면 채워넣기)

## 기술 스택

- **엔진**: Godot 4 (GDScript), 내장 고수준 멀티플레이(High-level Multiplayer API) 사용.
  근거: 씬/리소스가 텍스트 기반이라 git diff가 깨끗하고, 에디터 GUI 없이 CLI만으로도
  프로젝트를 다루기 쉬워서 사람 없는 헤드리스 루프에 적합하다.
- 도트 그래픽은 PixelLab에서 PNG로 생성해서 Godot에 텍스처로 임포트한다.

## 하네스 구조 (BUILD / DESIGN / QA)

루프는 세 종류의 세션(하네스)으로 나뉜다. 각각 다른 지시서(`loop/PROMPT_*.md`)를 쓰고,
INBOX.md 항목에 붙은 태그로 어떤 하네스가 처리할지 정해진다.

- **`[BUILD]`** (`loop/PROMPT_BUILD.md`): 게임 로직/기능을 만든다. 그림을 새로 만들지
  않는다 — 그림이 필요하면 `[DESIGN]` 항목을 새로 만들어서 넘긴다.
- **`[DESIGN]`** (`loop/PROMPT_DESIGN.md`): 스프라이트/애니메이션을 만든다. 무엇을
  만들기 전에 PixelLab의 공식 기능(특히 `animate-character`/`animate-with-skeleton`/
  `estimate-skeleton` 같은 애니메이션 전용 엔드포인트)부터 조사하고, 그걸로 안 될 때만
  손수 합성 같은 우회법을 쓴다.
- **`[QA]`** (`loop/PROMPT_QA.md`): 아무것도 만들거나 고치지 않는다. `[BUILD]`/`[DESIGN]`
  의 결과물을 실제로 플레이·스크린샷으로 관찰해서 문제를 찾아 새 항목(정확한 태그를
  붙여서)으로 등록하는 것까지만 한다. 좁은 범위 QA는 "문제 없음"이 나올 때까지 같은
  범위의 QA 항목을 스스로 다시 큐에 추가한다(자기 재검증 루프, 아래 "QA 관찰 항목"
  절 참고). `[BUILD]`/`[DESIGN]` 항목을 합쳐 5개 완료할 때마다 전체를 훑는 "QA 전체
  스윕" 항목이 자동으로 큐에 추가된다.
- 근거: 만드는 세션과 검사하는 세션이 같으면 자기 채점이 되어 문제를 놓친다 —
  실제로 그런 일이 여러 번 있었다(도끼/곡괭이낫 통합이 통과 처리됐다가 나중에 다시
  결함이 발견됨). 세 하네스로 나누면 이 편향이 구조적으로 줄어든다.
- INBOX 항목에 태그가 없으면 `loop.sh`는 기본값으로 `[BUILD]`로 처리한다(옛 항목과의
  호환용) — 새 항목을 추가할 때는 반드시 태그를 붙일 것.

### 크레딧/사용량 한도에 걸렸을 때

`loop.sh`는 매 바퀴 `claude -p`의 출력에서 "credit balance is too low", "usage limit",
"rate limit exceeded", "quota exceeded" 같은 문구를 감지한다. 감지되면 그 바퀴를
마지막으로 **재시도하지 않고 루프 전체를 멈추고**, 상태 페이지
(`https://kimtuna.github.io/life_game/`)에 빨간 경고 배너로 표시한다. 근거: 크레딧이
부족한 상태에서 계속 재시도하면 매번 똑같이 실패하면서 시간만 흐른다 — 사람이 알아채고
해결한 뒤 `loop/ctl.sh start`로 다시 켜는 게 낫다.

**외부 도구(PixelLab/SpriteCook 등) 잔액 부족도 같은 방식으로 처리한다.** 이건 클로드
자체의 한도가 아니라서 `claude -p` 출력에 자동으로 안 뜨기 때문에, `[BUILD]`/`[DESIGN]`
세션이 **직접** 판단해서 알려야 한다: 처음 발견하면 STATUS.md에 기록만 하고 한 바퀴
더 기회를 주고, **바로 다음 바퀴도 똑같이 막혀 있으면** 표준 출력에 정확히
`EXTERNAL_TOOL_BLOCKED: <이유>`를 출력하고 세션을 끝낸다 — `loop.sh`가 이 문구를
크레딧 한도와 동일하게 취급해 루프를 멈추고 경고 배너를 띄운다. 근거: 실제로 이 판단
없이 여러 바퀴가 "잔액 확인 → 기록만 → 다음 바퀴" 를 반복해서, 잔액이 전혀 바뀌지
않는데도 세션이 계속 새로 열려 진전 없이 사용량만 소모된 적이 있었다.

## 범위 안

### 클라이언트 화면 흐름
- **메인 메뉴**: 플레이 / 설정 / 나가기 세 버튼.
- **플레이** → 캐릭터 슬롯 화면(3개 슬롯, 코어키퍼 스타일). 빈 슬롯을 고르면 캐릭터
  커스터마이징 화면으로 이동하고, 커스터마이징을 확정하면 월드가 만들어지며 입장한다.
  이미 캐릭터가 있는 슬롯을 고르면 그 캐릭터로 바로 월드에 입장한다.
- **설정** → 해상도 등 그래픽 옵션. 아래 "카메라 / 해상도" 참고.
- **나가기** → 애플리케이션 종료.

### 카메라 / 해상도 (PvP 공정성 규칙)
- 설정에서 해상도를 바꿀 수 있다.
- **해상도를 높인다고 화면에 더 멀리(더 넓게) 보이면 안 된다.** 해상도 변경은 화면
  비율(종횡비)과 선명도에만 영향을 줘야 하고, 카메라가 보여주는 실제 월드 범위(시야)는
  모든 해상도에서 동일해야 한다. 근거: PvP에서 해상도를 높인 플레이어가 더 멀리 보여서
  유리해지는 것을 막기 위함 — 화면 크기가 곧 정보 우위가 되면 공정하지 않다.

### 조작
- 이동: WASD
- 시야/조준 방향: 마우스로 회전
- **좌클릭: 지금 손에 든 도구의 동작.** 총이면 발사, 도끼면 벌목, 곡괭이면 채광, 낫이면
  채집/수확, 낚싯대면 낚시 시작 — 모든 도구가 총과 동일하게 좌클릭 하나로 동작한다.
  별도의 "상호작용 키"(예: F)는 두지 않는다.
- 우클릭: (총을 들고 있을 때) 장전된 탄종 전환 (기본탄 ↔ 마취탄)
- 숫자키 1~9: 인벤토리 맨 위 9칸(핫바)에서 아이템을 골라 손에 든다. 아래 "인벤토리 / 장비" 참고.
- E: 인벤토리 창 열기/닫기

### 전투
- 총기 기반 전투. 총마다 세부는 다르지만 기본은 "조준선을 대상에 놓고 쏜다".
- 탄종: 기본탄, 마취탄 (그 외 탄종은 미정)
- **포획**: 대상 동물의 체력이 10% 미만으로 떨어진 상태에서 마취탄에 맞으면 포획할 수 있다.
- PvP 지원 (플레이어 대 플레이어 전투)

#### 총기 스탯 (1차 초안 — AI가 임의로 정함, 밸런스는 나중에 조정)
지금은 총 하나만 있다. **기본 소총**:
- 사거리: 800 (게임 단위 — 화면에서 대략 절반 정도를 커버하는 거리감)
- 데미지(기본탄/마취탄 공통): 25
- 연사 속도: 초당 2발 (사격 간격 0.5초)
- 탄퍼짐: 멈춰서 쏘면 거의 없음, 이동하면서 쏘면 커짐
- 반동: 연속 사격 시 조준선이 위로 살짝 튀고, 사격을 멈추면 빠르게 원래대로
- 아래 사슴 최대 체력(100)과 맞춰서 정한 숫자다 — 4방이면 처치, 마취탄으로는 체력 10(=10%) 아래일 때 포획 가능.
- **탄창**: 8발. 다 쏘면 좌클릭해도 발사되지 않고, **R키로 재장전**한다(약간의 시간 소요).
  예비 탄약(재장전 횟수 제한)은 아직 없다 — R을 누르면 항상 가득 재장전된다(범위 밖: 예비
  탄약을 아이템으로 관리하는 것). 탄창에 남은 발수를 화면에 표시한다.
- **기본탄과 마취탄은 서로 다른 탄창(잔여 발수)을 따로 관리한다.** 우클릭으로 탄종을
  바꾸는 것은 "다른 탄창으로 갈아 끼우는 것"과 같다 — 기본탄을 다 쓰고 마취탄으로
  바꿔도 마취탄 탄창은 그대로 가득 차 있어야 한다(하나의 탄약 수를 공유하면 안 됨).

### 생활 스킬 — 채집 계열
- **사냥**: 총으로 동물을 공격해서 잡는다.
- **벌목**: 도끼. (아직 벌목 대상인 "나무" 자원은 만들어지지 않음 — 범위 밖 참고)
- **채집 + 채광**: **곡괭이낫**(하나의 도구)으로 채집 포인트와 채광 포인트 양쪽 다 쓴다.
  근거: 채광 포인트를 나중에 "광산"으로 확장하면서 그 안에 추가 채집물도 놓을 계획이라,
  처음부터 도구를 합쳐뒀다 (아래 결정 로그 — 한때 곡괭이/낫을 분리했다가 되돌림).
- **낚시**: 낚싯대. 다른 채집 대상은 필드 아무 데나 있지만, 낚시는 **바다의 "낚시 스팟"** 에서만 가능하다.
  **낚싯대는 낚시 스팟 밖에서는 좌클릭해도 낚시하는 모션이 나오면 안 된다** — 총/도끼/
  곡괭이낫과 달리 근접무기로 확장할 계획이 없고, "특정 장소에서만 되는 행동"이라는 게
  낚시의 정체성이라 아무 데서나 휘두르는 모션이 있으면 오히려 혼란스럽다. (지금 #23이
  만든 "낚시 스팟 없이도 좌클릭 시 최소 반응" 동작은 낚시 스팟 자체가 아직 없어서 임시로
  넣어둔 것 — 낚시 스팟이 생기면 그 스팟 안에서만 모션이 나오게 바꿔야 한다.)
- 위 4개 도구(총/도끼/곡괭이낫/낚싯대)는 전부 인벤토리에 들어가는 아이템이고, 핫바에서
  선택해서 손에 들어야 쓸 수 있다.
- **총/도끼/곡괭이낫은 대상이 없어도(허공에 대고) 좌클릭하면 항상 사용 모션이 나와야
  한다.** 근거: 나중에 이 도구들에 공격력을 부여해서 근접무기로도 쓸 계획이라, "유효한
  채집/채광 대상이 있을 때만 모션이 나가는" 지금의 곡괭이낫 같은 방식이면 근접 공격
  자체가 성립하지 않는다. 낚싯대는 위 예외(스팟 안에서만) 참고.

#### 첫 번째 예시 자원 (하나씩만 — 나중에 늘림)
- 작물(채집으로 얻는 씨앗 대상): **벼**
- 동물(사냥/포획 대상): **사슴** (최대 체력 100 — 위 총기 스탯과 맞춰 정함)
- 광물(채광 대상): **철**
- 지금은 이 셋만 만든다. 종류를 더 늘리는 건 다음 INBOX 지시로 처리한다.
- 채집/채광 포인트는 다 캐면 회색으로 표시하는 대신 **완전히 사라졌다가**, 쿨다운이 끝나면
  다시 나타난다.

### 아이템 획득 방식 — 바닥 드롭
- 사냥/벌목/채집/채광으로 얻는 아이템은 곧바로 인벤토리에 들어가지 않는다. 대상 위치에
  아이템이 **바닥에 드롭**되고, 플레이어가 가까이 다가가면 자동으로 주워서 인벤토리에
  들어간다 (따로 습득 버튼은 없음 — 좌클릭은 도구 동작에 쓰므로 습득은 접촉으로 처리).

### 인벤토리 / 장비
- **일반 슬롯 18칸.** 그중 **맨 위 9칸이 핫바**를 겸한다 — 숫자키 1~9로 그 칸의
  아이템을 손에 든다(코어키퍼 방식: 핫바가 인벤토리와 분리된 별도 UI가 아니라 인벤토리의
  일부).
- **장비 슬롯 9칸** (일반 18칸과는 별개): 모자 1, 상의 1, 하의 1, 신발 1, 목걸이 2, 반지 2,
  가방 1. 장비 슬롯에 넣은 아이템이 실제로 어떤 효과를 주는지는 아직 안 정해짐 (범위 밖).
- E 키로 인벤토리 창을 열고 닫는다.
- 인벤토리 창이 열려 있을 때, 마우스로 아이템을 **드래그**해서 슬롯 사이(일반↔일반,
  일반↔장비, 핫바 포함)로 옮길 수 있다. 인벤토리 창 **바깥으로 드래그해서 놓으면**
  그 아이템은 인벤토리에서 사라지고 플레이어 근처 바닥에 드롭된다 (버리기).

### 생활 스킬 — 생산 계열
- **농사**: 채집으로 얻은 씨앗을 심어서 진행한다. **심기는 도구가 아니라 씨앗 아이템을
  손에 든 상태에서 밭에 좌클릭**하면 된다. 수확은 곡괭이낫을 든 상태로 좌클릭.
- **목장**: 사냥 후 마취탄으로 포획한 동물을 사육한다. 목장 구역 경계는 실제 충돌체(담장
  등)로 막혀 있어서 동물이 안팎으로 통과할 수 없다 (위치를 강제로 되돌리는 방식이 아니라
  물리적으로 막는다). **풀어놓기**: 포획한 동물 아이템(예: captured_deer)을 핫바에서
  손에 든 상태로 목장 구역에 좌클릭하면 풀어놓아진다 (빈손 좌클릭이 아니라, 씨앗 심기와
  같은 "든 것으로 좌클릭" 패턴).

### 동물 AI
- 평소에는 배회(랜덤 이동)한다.
- 플레이어가 가까이 다가가거나 총에 맞으면 도망간다.
- **도주는 플레이어 반대 방향으로 일직선이 아니라 예측하기 어렵게 움직여야 한다**
  (지그재그/방향 변화 등). 일직선 도주는 맞추기 너무 쉬워서 사냥의 긴장감이 없다.

### 시간 / 계절 / 날씨
- **하루 길이: 20분 (낮 10분 + 밤 10분)**. 계절이 바뀌어도 이 길이는 그대로다.
- 날짜: 1·2·3월 = 봄, 4·5·6월 = 여름, 7·8·9월 = 가을, 10·11·12월 = 겨울.
- 비는 낮에도 밤에도 올 수 있고, 각각 독립적으로 랜덤이다 (낮에만/밤에만/둘 다/둘 다 아님 전부 가능).
- **강수 확률 공식**: `그날의 강수확률 = 그 계절의 기본값 + (마지막으로 비 온 뒤 지난 날 수) × 1%p`.
  비가 온 날(낮이든 밤이든 하나라도 비가 왔으면)은 다음 날부터 다시 기본값에서 시작한다
  (스트릭이 리셋됨). 이 확률로 낮/밤을 각각 독립적으로 굴린다.
- **계절별 기본값**: 봄·가을·겨울 = 1%, **여름(4·5·6월) = 30%**(장마).

### 멀티플레이 — 세션 서버 아키텍처
- **호스트 겸용 리슨 서버**: 방을 만든 플레이어의 클라이언트가 그 세션의 서버 역할도 함께
  한다. 별도의 전용 게임 서버 프로세스는 두지 않는다.
- **방 코드**: 호스트가 "방 만들기"를 하면 짧은 방 코드(영숫자, 자릿수는 구현 시 정함)가
  발급된다. 다른 플레이어는 그 코드를 입력해서 방에 들어온다.
- 방 코드는 실제 접속 정보(호스트에게 어떻게 연결하는지)를 가리키는 키다. 서로 다른
  네트워크에 있는 플레이어끼리 포트포워딩 없이 코드만으로 연결되려면, 코드↔접속정보를
  중개해줄 작은 매치메이킹/릴레이 서버가 하나 필요하다 — 게임 클라이언트와는 별개의
  작은 인프라이며, 실제 만들 때 별도로 다룬다 (지금은 "이런 게 필요하다"만 기록).
- 게임 내부 상태 동기화는 Godot 내장 고수준 멀티플레이 API(ENetMultiplayerPeer)를 쓴다.
- **스팀 출시 예정**이므로, 나중에 Steam Networking Sockets(스팀 자체 P2P 릴레이 — NAT
  문제를 스팀이 대신 처리)로 연결 계층만 바꿔 낄 수 있도록, 지금부터 "연결 방식"과
  "게임 로직"을 분리해서 만든다. 스팀 SDK 연동 자체는 지금 범위에 없다 (범위 밖 참고).
- 동시 접속 인원 상한은 우선 작게 잡고(예: 4~8명) 나중에 필요하면 늘린다.

### 건축 / 방(Room) 시스템 (Oxygen Not Included 참고)
- **어디든 자유롭게 지을 수 있다.** 정해진 "건축 가능 구역" 같은 건 없다 — 코어키퍼처럼
  월드 어느 자리에나 건축 오브젝트를 놓을 수 있다. 격자(타일)에 맞춰 짓는지 여부는
  아직 정해지지 않았다(범위 밖 참고) — 격자는 여러 구현 방법 중 하나일 뿐, 필수가
  아니다.
- **재료를 가공해서 건축 오브젝트를 만든다.** 예: 나무를 가공해서 나무벽을 만드는 식.
  구체적인 가공 레시피(어떤 재료 몇 개로 뭘 만드는지)는 아직 정해지지 않았다.
- **방(Room) 인식**: 벽 등으로 막힌(둘러싸인) 공간이 생기면 자동으로 "방"으로 인식된다.
  그 방 안에 특정 조건(예: 특정 오브젝트가 있음)을 만족하면 방 이름이 자동으로 붙는다
  (예: 연구대가 있으면 "연구실"). 특정 카테고리의 오브젝트가 있으면 그 이름 조건을
  무효화할 수도 있다(예: 산업 구조물이 있으면 연구실이 될 수 없음).
- **방 종류별 구체적인 규칙표(어떤 방이 뭘 요구하는지, 뭘 금지하는지)는 지금 정하지
  않는다** — 나중에 별도 데이터(또는 게임 내 튜토리얼/도감)로 정리할 예정이다. 지금은
  "이런 매커니즘이 있다"는 것만 기록해둔다.
- 이 시스템은 나중에 추가할 **생산 자동화**(농사/목장 자동화 기계 등)와 **플레이어가
  직접 집을 짓는 것**을 지원하기 위한 기반이다 — 자동화 자체는 아직 범위에 없다(범위
  밖 참고).

## 캐릭터 애니메이션 (중요 규칙 — #41에서 구조 확정, 절대 되돌리지 말 것)

- **캐릭터는 정지 이미지 한 장이 아니라, 방향별로 여러 프레임(그림 여러 장)을 빠르게
  갈아끼우는 방식(2D 게임의 표준적인 "스프라이트 시트" 애니메이션 — 뼈대/스켈레톤
  애니메이션이 아니다)으로 움직인다.** Godot의 `AnimatedSprite2D`(`SpriteFrames`)를 쓴다.
  최소한 방향별 idle(1프레임 이상)과 walk(4~6프레임) 애니메이션이 있어야 한다.
- **서로 다른 생성 호출로 만든 프레임끼리 캐릭터가 차지하는 크기(픽셀 비율)가 달라지면
  안 된다** — 예: idle과 walk, 또는 east와 west를 각각 따로 생성하면 캔버스 크기(가로x세로
  픽셀)는 같아도 그 안에서 캐릭터를 확대/축소한 정도가 서로 달라질 수 있다(실제로
  `walk_0`이 idle보다 크게, `gun_west_idle`이 `gun_east_idle`보다 작게 나온 적이 있다).
  프레임을 만들고 나면 반드시 같은 세트 안에서 캐릭터 크기를 직접 비교해서 맞출 것.
- **애니메이션 프레임 사이의 움직임이 자연스럽게 이어져야 한다.** 걷기 프레임을 순서대로
  넘겨봤을 때 다리/팔이 매끄럽게 움직이는 것처럼 보여야지, 중간에 자세나 크기가 뚝뚝
  끊겨 보이면 안 된다. idle에서 사용(발사/채광 등) 모션으로 바뀔 때도 자세가 갑자기
  다른 캐릭터처럼 변하지 말고 자연스럽게 이어지는 느낌이어야 한다. (2026-09-03,
  사용자 지시) — 앞으로 만드는 모든 도구/오브젝트 애니메이션에 항상 적용한다.
- **"도구 관련 모션" 좁은 범위 QA 품질 확인 완료 (2026-09-04, INBOX #75).** 총/도끼/
  곡괭이낫/낚싯대 4개 전부 green 기준으로 4방향(south/east/north/west) x idle/사용
  (이동하면서 좌클릭, 곡괭이낫은 채광·채집 둘 다)/사용 안 하고 이동만 상태를 실제
  화면 스크린샷(`game/qa/tool_motion_sweep.gd`)으로 직접 확인함. (1) 도구별 idle
  캐릭터 크기가 4방향 서로 일치하고 맨손/다른 도구와 비교해도 어긋나지 않음(#70/#71/
  #74가 다뤘던 크기 불일치 재발 없음). (2) 이동 중 좌클릭 시 각 도구의 사용 모션
  (발사 섬광/도끼 스윙/곡괭이낫 채광·채집/낚싯대 낚시)이 4방향 전부 정상적으로
  나타남(`_current_animation_name()`이 이동 여부와 무관하게 사용 중엔 사용 애니메이션을
  우선함, `player_sprite.animation` 값으로도 확인). (3) 사용하지 않고 이동만 하면
  도구가 사라지고 맨손 walk 애니메이션으로 자연스럽게 전환됨(#65 의도대로 동작).
  결함 0건 — 재확인 루프 종료.

## 아이템/오브젝트 크기 표준 (2026-09-03, 앞으로 나올 모든 아이템에 항상 적용)

- **기준 크기**: 플레이어가 화면에서 차지하는 높이는 약 102px(캔버스 68px × 씬 스케일
  1.5배)다. 이걸 "보통 크기" 기준점으로 삼는다.
- **최소 크기**: 도구/드롭 아이템/작은 채집물처럼 "특별히 커야 할 이유가 없는" 오브젝트는
  화면에서 **최소 32px**(가로/세로 중 짧은 쪽 기준) 이상으로 보이게 만든다 — 이미 도구
  아이콘들(`assets/sprites/tools/*.png`)이 32×32로 통일돼 있어서 이 값을 하한선으로
  그대로 쓴다. **이보다 작게 만들지 않는다** — 너무 작으면 화면에서 잘 안 보인다.
- **큰 오브젝트는 커도 된다**: 나무, 큰 가구, 벽/건축물, 목장 같은 구역, 덩치 큰 동물처럼
  원래 커야 하는 것은 이 최소 크기보다 훨씬 커도 상관없다 — 이 규칙은 하한선이지 상한선이
  아니다. 다만 그 카테고리 안에서는(예: 나무들끼리) 서로 크기가 들쭉날쭉하지 않게 통일할 것.
- 새 아이템을 만들 때마다 "이게 특별히 커야 하는 이유가 있는가?"를 먼저 판단하고,
  없으면 위 최소 크기 기준을 지키고, 있으면 플레이어 크기(102px)와 비교해서 비율이
  터무니없지 않은지(예: 주먹만 한 도끼가 플레이어보다 커지는 등) 확인한다.
- 이전(#4~#40)에는 `Sprite2D` 하나에 방향별 정지 이미지 한 장만 텍스처로 갈아끼우는
  방식이었다 — 그래서 걷는 동안 다리가 전혀 움직이지 않아 부자연스러웠다. #41부터
  `AnimatedSprite2D` 기반으로 바꾼다.
- **도구는 캐릭터 옆에 별도 아이콘을 띄우는 방식(#22~#40에서 쓰던 `_held_item_sprite`
  오프셋 방식)을 쓰지 않는다.** 대신 도구를 든 캐릭터의 "들고 있는 모션"과 "실제로 쓰는
  모션" 프레임 자체에 도구를 쥔 손 모양을 그려 넣는다 — 즉 도구별로 캐릭터 전체가 다시
  그려진 애니메이션 프레임 세트(방향별)가 생긴다: 총(들고 있기/발사), 도끼(들고 있기/
  패기), 곡괭이낫(들고 있기/채광하기/채집하기 — 이 둘도 서로 다른 동작), 낚싯대(들고
  있기/낚시하기).
- 근거: 아이콘을 캐릭터 옆에 띄우고 위치만 옮기는 방식(오프셋 조정)을 여러 번
  시도했지만 사용자가 계속 "여전히 이상하다"고 판단했다(INBOX #35, #37~#40 이후에도
  재지적됨) — 캐릭터 자체가 정적이고 도구가 손과 무관하게 붙어 있어서 생기는 구조적
  문제였다. 코드 조정(오프셋/z_index)으로는 한계가 있고, 캐릭터+도구를 하나의 그림으로
  통합해서 다시 그려야 한다.
- **(2026-09-03 발견된 빠뜨림) 도구별 애니메이션에는 "들고 있기"/"사용하기" 말고도
  반드시 "그 도구를 든 채 걷기" 세트도 있어야 한다.** `_current_animation_name()`이
  `_held_tool`이 있으면 이동 여부(`_is_moving`)를 아예 확인하지 않아서, 도구를 든 채
  이동하면 idle/사용 포즈로 얼어붙은 채 움직이는 버그가 있었다(총으로 처음 발견됨).
  앞으로 도구 애니메이션 세트를 만들 때는 idle/사용 + **walk**까지 세 가지를 기본으로
  친다.

## 그래픽 파이프라인 (중요 규칙)

- **캐릭터/동물처럼 관절이 있는 유기체 형태는 반드시 AI 생성 도구로 만든다. 손으로
  (코드로 직접 좌표를 찍어) 그리지 않는다.** 근거: 손으로 그리면 외곽선이 뭉개지고
  선이 떨려서, 다른 사람이 봤을 때 퀄리티가 바로 티가 난다 — 이 프로젝트에서 실제로
  겪은 문제(사슴, 도구 든 자세)가 전부 이 종류였다.
- **도구/나무/돌/광물 같은 단순한 정적 오브젝트는 예외적으로 파이썬(Pillow 등) 절차적
  생성을 시도해볼 수 있다** — 다만 이것도 결과물이 ①(합격 기준)을 스크린샷으로 통과해야
  한다. 통과 못 하면 코드를 더 다듬지 말고 AI 생성 도구로 다시 만든다(이 예외가 "안 되면
  계속 코드로 우겨넣기"의 핑계가 되면 안 된다).
- **캐릭터/동물 애니메이션 전담 도구는 SpriteCook.** 정적 오브젝트/아이템 아이콘은
  PixelLab이나 SpriteCook 아무거나(또는 위의 절차적 생성) 써도 된다. 근거: SpriteCook은
  캐릭터를 만들면 idle/walk/attack/run 같은 모션을 한 번에 뽑아주는 기능이 있어서 지금
  겪고 있는 문제(걷기/도구 모션)에 더 직접적으로 맞는다.
  - PixelLab(`PIXELLAB_API_KEY`)은 2026-09-03 기준 잔액 $0 — 충전 전까지 호출이
    안 될 수 있다. 먼저 잔액을 확인하고 안 되면 SpriteCook으로 전환할 것.
  - SpriteCook(`SPRITECOOK_API_KEY`)은 구독 전이라 기본 무료 크레딧만 있다 — 실패한
    시도를 반복해서 낭비하지 말고, 계획을 세운 뒤 신중하게 호출할 것.
- API 키는 코드나 md 파일에 직접 적지 않는다. `loop/secrets.env`(git에 커밋되지 않음)에
  `PIXELLAB_API_KEY`/`SPRITECOOK_API_KEY` 환경변수로 들어있고, `loop.sh`가 매 바퀴 세션을
  열 때 이 환경변수를 자동으로 물려준다 — 세션은 그냥 환경변수를 읽어서 쓰면 된다.
- 생성 도구로 여러 결과를 만든 뒤, 그중 괜찮은 것을 골라서 채택한다(생성 → 검수 → 채택).
  API 스펙(엔드포인트/파라미터)은 필요할 때 직접 조회해서 확인한다.
- **여러 색상 × 여러 방향 × 여러 모션을 한 번에 다 만드는 INBOX 항목을 만들지 않는다.**
  먼저 기준 색상 1개(보통 green)로 필요한 방향·모션 전체를 완성해서 품질 검증까지
  끝내는 항목 하나, 그다음 그 방식을 나머지 색상(blue/red 등)에 그대로 적용해서
  확장하는 항목 하나 — 이렇게 최소 두 항목으로 쪼갠다. 근거: 색상×방향×모션 조합을
  한 번에 다 만들면 한 바퀴 예산/시간 안에 못 끝내고 커밋 직전에 죽는 일이 반복됐다
  (도끼/곡괭이낫/낚싯대 통합 때 전부 이 패턴으로 최소 한 번씩 죽었다 — STATUS.md 참고).
  쪼개두면 중간에 죽어도 손실이 색상 하나 분량으로 줄어든다.

## QA 관찰 항목 (자기 재검증 루프)

지금까지 QA는 매 바퀴 임시 스크립트로 스크린샷을 찍고 그 바퀴가 스스로 판단한 뒤
지워버리는 방식이었다 — 그래서 같은 종류의 지적("여전히 이상하다")이 반복됐다. 이제
"만들기" 항목과 별도로 **"QA 관찰" 항목**을 INBOX에 넣을 수 있다. 형식은 이렇다:

1. **목표 범위를 좁게 지정한다** (예: "총을 든 캐릭터 4방향 idle + 발사 모션"). 한 번에
   여러 도구/시스템을 다 보려 하지 않는다.
2. 그 범위를 실제로 스크린샷으로 찍고(방법은 STATUS.md의 기존 결정 로그를 먼저 확인 —
   헤드리스 렌더 캡처법, 마우스 조준을 강제로 바꾸는 우회법 등이 이미 정리돼 있다),
   **Read 도구로 그 이미지를 직접 열어서 눈으로 본다** (코드 로직만으로 "괜찮다"고
   판단하지 않는다).
3. DESIGN.md가 기준으로 든 참고 게임(스타듀밸리/코어키퍼)과 구체적으로 비교해서 이상한
   점을 하나하나 찾는다. "자연스럽다"/"이상하다" 한 줄로 끝내지 말고, 어디가 왜 이상한지
   서술한다.
4. **이상한 점을 찾았다면**: 그 하나하나를 새 INBOX 항목으로 추가한다(발견만 하고 이
   항목 안에서 고치지는 않는다 — 고치는 건 뒤에 추가된 항목들이 각자 한 바퀴씩 맡는다).
   그리고 그 새 항목들 바로 뒤에 **지금 이 QA 관찰 항목과 똑같은 내용의 "QA 재확인"
   항목**을 하나 더 추가한다. 이렇게 해야 고친 뒤에 다시 검증하는 루프가 사람 개입 없이
   이어진다.
5. **이상한 점을 하나도 못 찾았다면**: 새 항목을 추가하지 않는다(이게 이 범위에 대한
   루프의 자연스러운 종료 조건이다). 대신 DESIGN.md나 STATUS.md에 "이 범위는 품질 확인
   완료(날짜)"라고 기록해서 다음에 또 같은 걸 재검증하지 않게 한다.
6. QA 관찰 항목은 그림/애니메이션을 새로 만들지 않는다(비용이 커지지 않게) — 순수하게
   "보고 → 판정 → 티켓 발행"만 한다.

## 완성의 기준

(전체 게임의 "다 됐다" 기준은 아직 정해지지 않음. 바퀴별 합격 기준은 아래 공통 기준과
`loop/PROMPT_BUILD.md`/`PROMPT_DESIGN.md`/`PROMPT_QA.md`(아래 "하네스 구조" 참고)의
①을 따른다.)

**공통 합격 기준 (모든 바퀴에 적용)**: 다른 사람이 봤을 때도 퀄리티가 떨어지지 않는가가
최우선 기준이다. 이 기준을 통과하지 못하면 커밋하지 않는다.

**(2026-09-03, 사용자 지시로 현재 단계의 기준 조정 — [DESIGN] 한정) 지금은 예술적
완성도보다 "기본이 지켜지는가"를 우선한다.** 계속 완벽한 퀄리티를 추구하다가 진도가
안 나가서, 사용자가 명시적으로 기준을 낮춰달라고 요청했다. 구체적으로 "기본"이란:
- **상태가 빠지면 안 된다** — 예: 도구를 든 채 이동하면 걷기 프레임이 있어야 한다
  (idle/사용 포즈로 얼어붙어 있으면 안 됨).
- **서로 다른 상태(idle vs 사용/발사)는 시각적으로 구별돼야 한다** — 완전히 같은
  그림이면 안 된다. 대단히 정교할 필요는 없다.
- **방향 4개가 서로 크게 어긋나면 안 된다** — 예: 한 방향은 무기를 조준한 자세인데
  다른 방향은 무기를 늘어뜨린 자세인 것처럼, 방향마다 기본 자세 자체가 달라 보이면
  안 된다.
이 세 가지만 지키면 통과로 본다. 미세한 손 위치, 프레임 수, 그림체의 정교함 같은 건
지금 단계에서 더 다듬지 않는다 — 게임 기능(BUILD) 진행이 막히지 않는 게 우선이다.
나중에 여유가 생기면 다시 다듬는 지시가 올 수 있다.

## 캐릭터 스타일 목표 (참고 이미지 기반, 2026-09-04)

사용자가 지금 캐릭터 기본 그림체가 원하는 감성과 안 맞는다고 판단해서, 두 장의 참고
이미지를 기준으로 캐릭터(사람/동물 등 유기체) 그림을 다시 만들기로 함. 참고 이미지는
`docs/design_reference/style_ref_dragon.png`(드래곤)와
`docs/design_reference/style_ref_fisherman.png`(낚시꾼 NPC) — DESIGN 작업을 시작하기 전
Read 도구로 이 두 파일을 먼저 열어서 눈으로 직접 확인할 것(설명 텍스트만 보고 넘어가지
말 것).

**이 스타일의 구체적 특징 (말로 옮긴 것 — 그림을 직접 보는 걸 대체하지 않음)**:
- **다부호(chibi) 비율**: 머리가 몸통에 비해 크고, 전체 키가 머리 2.5~3개 높이 정도로
  작고 귀여운 비율. 지금 게임 캐릭터처럼 성인 비율로 늘어져 있지 않다.
- **순색 블록이 아니라 톤 단계가 있는 음영**: 같은 면(예: 옷, 피부, 비늘) 안에서도
  밝은 톤/중간 톤/어두운 톤 2~3단계로 부드럽게 나뉘어 입체감이 있다. 지금 게임처럼
  한 부위가 완전히 단일 색 블록으로 뭉개져 있지 않다.
- **순수 검정 외곽선 없음**: 외곽선이 있어도 그 부위 색보다 어둡고 채도 낮은
  남색/갈색 계열이지, `#000000` 순검정이 아니다. 그래서 선이 딱딱하지 않고 전체
  그림이 부드러워 보인다.
- **채도를 낮춘 차분하고 조화로운 팔레트**: 원색을 강하게 쓰지 않는다(드래곤의
  청회색·자주색, 낚시꾼의 갈색·베이지·짙은 남색 모자 등 — 전부 서로 튀지 않고
  어울리는 톤).
- **단순화된 표정/디테일**: 얼굴은 점 눈+간단한 미소 정도로 단순하지만, 작게 봐도
  실루엣과 정체(무엇을 들고 있는지 등)가 바로 읽힌다.

**적용 범위**: 이 스타일 목표는 캐릭터(플레이어/동물 등 유기체) 그림에만 적용된다.
도구 아이콘이나 정적 오브젝트(나무/돌 등)는 위 "그래픽 파이프라인"의 절차적 생성
허용 범위와 별개 — 그쪽은 지금 이 스타일 목표를 따라야 할 필요는 없다(다만 전체
분위기가 크게 튀지 않게 팔레트 정도는 참고할 수 있음).

**"완성의 기준"과의 관계**: 위 "완성의 기준"(2026-09-03)의 "기본만 지키면 됨" 기준은
상태 누락/구별/방향 어긋남처럼 **기능적** 최소선이고, 이번 캐릭터 리메이크는 그것과
별개로 **그림체 자체**를 이 절의 기준에 맞추는 게 목적이다 — 즉 리메이크 결과물은
"기본 기준"뿐 아니라 위에 적은 스타일 특징(비율/음영 단계/외곽선 색/팔레트)도 참고
이미지와 비교해서 실제로 닮았는지까지 확인해야 통과로 본다.

## 주요 결정과 이유

- 그래픽은 PixelLab AI 생성물만 쓰고 손으로 그리지 않기로 함. 근거: 위 "그래픽 파이프라인" 참고.
- (2026-09-04) 캐릭터 기본 그림체를 참고 이미지 2장 기준으로 전면 재작업하기로 함.
  근거(사용자 설명): 지금 캐릭터가 원하는 "말랑한" 도트 감성과 안 맞고, 아직 게임
  규모가 작을 때 고치는 게 나중에 콘텐츠가 쌓인 뒤 고치는 것보다 수월하다. 절차적
  생성(파이썬)은 이번 리메이크에 쓰지 않는다 — 사용자가 파이썬 절차적 생성의 성공
  사례(잔디 텍스처)를 근거로 캐릭터에도 못 쓰는지 물었으나, 확인 결과 그 성공은
  "반복 패턴/텍스처"라는 수학적으로 풀리는 문제였고, 이번에 필요한 건 유기적 실루엣/
  비율/음영 표현이라 위 "그래픽 파이프라인"의 기존 구분(유기체=AI 생성 필수)이 그대로
  적용된다 — 이 구분은 이미 하네스에 있던 규칙이었음(새로 정한 게 아님). 자세한 스타일
  기준은 위 "캐릭터 스타일 목표" 절 참고.
- 강수 확률은 낮게 시작해서(1%) 매일 누적 상승시키기로 함. 근거: 낮/밤 비 여부를 각각
  독립적으로 랜덤 처리하면 하루에 비가 올 확률 자체가 높아지므로, 기본값을 낮게 눌러야 함.
- 엔진은 Godot 4(GDScript)로 정함. 근거: 위 "기술 스택" 참고 — 무인 헤드리스 루프가
  다루기 쉬운 텍스트 기반 프로젝트 구조가 최우선 고려사항이었음.
- 총기 스탯(사거리 800/데미지 25/연사 초당 2발)과 사슴 최대 체력(100)을 서로 맞춰서
  정함. 근거: 마취탄 포획 조건(체력 10% 미만)이 실제로 의미 있으려면 데미지와 체력이
  숫자로 맞아떨어져야 해서, 임의로 정하되 두 숫자를 짝지어 정함.
- 채집물/동물/광물은 벼·사슴·철 하나씩만 먼저 만들고 나중에 늘리기로 함. 근거: 종류를
  늘리는 건 반복 작업이라 시스템(농사/사냥/채광 로직) 자체를 먼저 검증하는 게 우선.
- 강수 확률은 "계절 기본값 + 마지막 비 이후 지난 날 수 × 1%p, 비 오면 리셋" 공식으로
  확정함. 여름 기본값 30%에도 같은 공식이 적용됨.
- 하루 길이를 20분(낮 10분/밤 10분)으로 고정함, 계절별 변화 없음.
- 세션 서버는 호스트 겸용 리슨 서버 + 방 코드 발급/입력 방식으로 정함. 근거: 스팀
  출시 예정이라 나중에 Steam Networking Sockets로 연결 계층을 교체할 가능성이 높아,
  지금부터 연결 방식과 게임 로직을 분리해두기로 함.
- 상호작용 키(F)를 없애고 모든 도구(총 포함)를 좌클릭 하나로 통일함. 근거: 사용자가
  F키 상호작용 방식을 명시적으로 거부했고, 총이 이미 좌클릭으로 동작하므로 다른 도구도
  같은 방식으로 맞추는 게 일관적이다.
- 채집 도구를 삽 대신 낫으로 바꾸고, 곡괭이와 분리된 별도 아이템으로 정함(총/도끼/곡괭이/
  낫/낚싯대 5개, 전부 인벤토리 아이템). 근거: 사용자가 직접 도구 목록을 다시 지정함 —
  삽+곡괭이를 "한 세트로 자동 적용"하던 이전 방식(도구 인벤토리 개념 자체가 없었음)을
