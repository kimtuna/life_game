# PROMPT.md — 이번 바퀴 지시서

> 이 파일은 매 바퀴 새로 열리는 세션에게 그대로 전달됩니다.
> 세션은 이전 바퀴의 대화를 기억하지 못합니다. 기억은 아래 문서(STATUS, INBOX 등) 파일이 대신합니다.

---

## ① 합격 기준 (한 문장)

다른 사람이 봤을 때도 퀄리티가 떨어지지 않는가가 최우선 기준이다 — 이 기준을 통과하지
못하면 (빌드가 되고 기능이 동작하더라도) 커밋하지 않는다.

---

## ② 먼저 읽을 문서

아래 순서대로 읽고 시작한다.

1. `docs/feedback/INBOX.md` — "처리 대기"에서 번호(`#N`)가 가장 작은 미완료(`- [ ]`) 항목 하나. 이번 바퀴는 이 항목 하나만 처리한다. (loop.sh가 큐가 빈 경우엔 애초에 세션을 열지 않으므로, 이 파일이 열렸다는 것은 처리할 항목이 최소 하나 있다는 뜻이다.)
2. `docs/STATUS.md` — 전체.
3. `docs/DESIGN.md` — **전체를 빠짐없이 읽는다.** 새로 열리는 이 세션이 이 프로젝트에
   대해 아는 것은 md 파일이 전부다. 이번 항목과 무관해 보이는 절도 건너뛰지 않는다 —
   건너뛰면 이미 정해진 설계와 어긋나게 만들거나 같은 걸 다시 만들 위험이 크다.

---

## ③ 규칙과 근거

- **이번 바퀴는 INBOX.md 항목 정확히 1개만 처리한다.** 근거: 무한 루프는 바퀴마다 토큰(비용)이 나간다. 한 바퀴에 여러 항목을 욕심내면 실패했을 때 어디까지 됐는지 추적하기 어렵고, 커밋 단위도 커져서 ⑤의 "작게 자주 커밋" 원칙과 충돌한다.
- **세션 안에서 직접 `git push`를 실행하지 않는다.** 근거: push는 loop.sh가 바퀴 종료 후 대시보드 커밋과 함께 한 번에 처리한다. 세션이 직접 push하면 순서가 꼬이거나 두 번 push되어 충돌할 수 있다.
- **완료한 INBOX 항목은 `- [ ]` → `- [x]`로 바꾸고 완료 날짜를 붙인다. 지우지 않는다.** 근거: 지우면 다음 바퀴(또는 사람)가 "이미 처리됐다"는 사실을 알 방법이 없어 같은 일을 반복하거나 되돌릴 수 있다.
- **`docs/DESIGN.md`가 비어 있거나 이번 항목과 무관해 보여도, 항목 내용에 없는 기능을 임의로 지어내지 않는다.** 근거: 시험 실행에서 실제로 이 판단이 안전하게 작동함을 확인했다 — 정의되지 않은 범위를 추측하면 다음 바퀴가 서로 다른 방향으로 되돌릴 위험이 크다. 판단이 필요하면 STATUS.md의 "막힌 것/보류"에 적고 INBOX 항목은 완료 처리하지 않는다.
- **그림(도트 그래픽)은 손으로 그리지 않고 PixelLab로 생성한다.** 근거: `docs/DESIGN.md`의 "그래픽 파이프라인" 참고 — 손으로 그리면 외곽선이 뭉개지고 선이 떨려서 ①의 합격 기준을 못 넘긴다. API 키는 `PIXELLAB_API_KEY` 환경변수로 이미 주어져 있다 (직접 값을 코드/문서에 적지 않는다).

## ④ 한 바퀴 도는 순서

1. 읽기 — 위 ②의 문서를 순서대로 읽는다. INBOX.md에서 이번에 처리할 항목 번호(`#N`)를 확정한다.
2. 하나만 만들기 — 확정한 INBOX 항목 하나만 처리한다. 다른 항목이나 이번 지시에 없는 작업을 함께 벌이지 않는다.
3. 실행해서 눈으로 확인 — 코드를 실행해 실제로 동작하는지 확인한다. "빌드가 된다"와 "의도한 대로 동작한다"는 다른 문제다. ①의 합격 기준(다른 사람이 봐도 퀄리티가 떨어지지 않는가)을 이 시점에 스스로 판정한다.
4. 커밋 — 3번에서 ①을 통과하지 못했다면 커밋하지 않는다(진행 상황과 이유는 STATUS.md에 남긴다, INBOX 항목은 미완료로 둔다). 통과했다면 ⑤의 순서와 커밋 메시지 형식을 따른다.
5. `docs/STATUS.md` 갱신 — 섹션마다 쓰는 방식이 다르다. 헷갈리지 말 것:
   - **끝난 것 / 다음에 할 것 → 덮어쓴다 (스냅샷).** 지난 바퀴들이 뭘 했는지는 이미 git
     커밋 메시지(`[INBOX #N] ...`)에 상세히 남아있으니 여기서 또 누적하지 않는다.
     "지금 기준으로 어디까지 왔고 다음에 뭘 할지"만 최신 상태로 다시 쓴다.
     "다음에 할 것"을 비워두면 다음 바퀴가 이어받을 자리를 모른다 — 반드시 채운다.
     왜 그렇게 정했는지도 함께 남긴다. 이유가 없으면 다음 바퀴가 되돌릴 수 있다.
   - **막힌 것 / 보류 → 안 풀린 항목은 유지하고, 새로 생긴 것만 추가한다.** 풀렸으면
     그 항목을 지운다.
   - **결정 로그 → 계속 추가만 한다. 지우지 않는다.** 지금까지 내려진 결정의 최종 기록이다.
   - `docs/feedback/INBOX.md`의 해당 항목을 `- [x]`로 바꾸고 완료 날짜를 붙인다 (지우지 않는다).

## ⑤ 커밋 순서 규칙

- 검사(빌드/테스트/실행)를 통과하면, 결과 화면을 사람이 보기 "전에" 먼저 커밋한다.
- 한 바퀴는 예산이나 시간 제한으로 도중에 멈출 수 있다. 멈춘 자리에 커밋이 없으면 그 작업은 그대로 사라진다.
- 즉: 작게 자주 커밋한다. 큰 작업을 다 끝낸 뒤 한 번에 커밋하지 않는다.
- push는 하지 않는다 (③ 참고, loop.sh가 대신 처리한다).

### 커밋 메시지 형식

**제목**: `[INBOX #N] <이번 바퀴에서 실제로 한 일 한 줄>`
(N은 이번 바퀴에 처리한 INBOX 항목 번호)

**본문** — 아래 순서와 소제목을 그대로 쓴다. 해당 사항이 없는 절은 "없음"이라고 쓴다 (절 자체를 생략하지 않는다):

```
<전체 요약 1~2문장 — 무엇을 왜 했는지>

## 스스로 판단해서 고친 부분
- (지시받은 내용과 다르게, 더 낫다고 판단해 바꾼 부분을 먼저 적는다.
   예: "총기 디자인이 게임 시대상과 안 맞아 다시 만듦")

## 지시받지 않았지만 추가한 개선
- (INBOX 항목에는 없었지만 하는 김에 고치거나 더한 것)

## 어려움 / 에러와 해결
- (막혔던 지점, 에러 메시지, 어떻게 풀었는지)
```

## ⑥ 검사와 QA

- 화면이 있는 것을 만들었다면, 실제로 실행해서 스크린샷을 찍고 그 이미지를 직접 읽어라. 코드가 돌아가는 것과 화면이 괜찮은 것은 다른 문제다.
- 같은 지적(사람이든 스스로든)이 두 번 나오면 그때는 규칙으로 올린다(③에 추가). 기계가 잴 수 있는 규칙이면 자동 검사로 만들어 둔다. 한 번 겪은 고장을 두 번 겪지 않는다.
