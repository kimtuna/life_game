# PROMPT_BUILD.md — [BUILD] 하네스: 기능/로직 구현

> 이 파일은 INBOX.md에서 `[BUILD]` 태그가 붙은, 번호가 가장 작은 미완료 항목을 처리할
> 때 매 바퀴 새로 열리는 세션에게 그대로 전달됩니다. 세션은 이전 바퀴의 대화를 기억하지
> 못합니다. 기억은 아래 문서(STATUS, INBOX 등) 파일이 대신합니다.
>
> 이 하네스는 **게임 로직/기능**을 만드는 담당이다. 그림/애니메이션 품질 자체를
> 판단하거나 새로 만드는 것은 `[DESIGN]` 하네스(`PROMPT_DESIGN.md`) 몫이고, 전체적으로
> 문제를 찾아내는 것은 `[QA]` 하네스(`PROMPT_QA.md`) 몫이다.

---

## ① 합격 기준 (한 문장)

다른 사람이 봤을 때도 퀄리티가 떨어지지 않는가가 최우선 기준이다 — 이 기준을 통과하지
못하면 (빌드가 되고 기능이 동작하더라도) 커밋하지 않는다.

---

## ② 먼저 읽을 문서

아래 순서대로 읽고 시작한다.

1. `docs/feedback/INBOX.md` — "처리 대기"에서 `[BUILD]` 태그가 붙고 번호(`#N`)가 가장
   작은 미완료(`- [ ]`) 항목 하나. 이번 바퀴는 이 항목 하나만 처리한다.
2. `docs/STATUS.md` — 전체.
3. `docs/DESIGN.md` — **전체를 빠짐없이 읽는다.** 새로 열리는 이 세션이 이 프로젝트에
   대해 아는 것은 md 파일이 전부다. 이번 항목과 무관해 보이는 절도 건너뛰지 않는다 —
   건너뛰면 이미 정해진 설계와 어긋나게 만들거나 같은 걸 다시 만들 위험이 크다.

---

## ③ 규칙과 근거

- **이번 바퀴는 INBOX.md `[BUILD]` 항목 정확히 1개만 처리한다.** 근거: 여러 항목을
  욕심내면 실패했을 때 어디까지 됐는지 추적하기 어렵고, 커밋 단위도 커져서 ⑤의 "작게
  자주 커밋" 원칙과 충돌한다.
- **새 제작 레시피(가공대/제련로/조리대/조리용 화로 등)를 추가할 때는 재료 종류를
  최대 1~2개로 얕게 유지한다** (DESIGN.md "생산 라인" 절 2026-09-04 규칙 참고) — 완성품
  하나를 만들려고 부품을 여러 단계 거쳐 조합하게 만들지 않는다. 근거: 부품을 너무 많이
  만들게 하면 플레이어에게 스트레스를 준다는 사용자 지시. 이 확인은 매번(예외 없이) 한다.
- **새 아이템 종류를 하나라도 추가하면(제작 결과물, 채집/채광 드롭 등), 같은 바퀴 안에서
  월드에 배치된 테스트용 저장 상자(`storage_chest`, INBOX #96/#97/#116/#117)에도 그
  아이템을 넉넉한 수량(999개 이상, #116 이후엔 무제한이므로 더 커도 됨)으로 채워
  넣는다.** 무료 지급 도구(총/도끼/곡괭이낫/낚싯대)와 생포 전용 `captured_deer`는
  예외(계속 제외). 근거(사용자 지시): 매번 사람이 "테스트 상자에도 넣어달라"고 다시
  요청하지 않아도, 새 아이템이 생기면 자동으로 테스트 가능한 상태가 유지돼야 한다.
  이 확인은 매번(예외 없이) 한다 — 잊었다면 그 사실을 STATUS.md에 남기고 별도 항목으로
  뒤늦게라도 채워 넣는다.
- **이 하네스는 새로운 도트 그래픽/애니메이션을 직접 만들지 않는다.** 기능 구현에
  그림이 필요한데 아직 없다면: (a) 이미 있는 자산(단순 도형이 아니라 기존 스프라이트)을
  최대한 재사용하거나, (b) 정말 새 그림이 필요하면 `docs/feedback/INBOX.md`에
  `[DESIGN]` 태그로 필요한 그림을 구체적으로 지시하는 새 항목을 추가하고, 이번 항목은
  `docs/STATUS.md` "막힌 것/보류"에 이유를 적고 미완료로 둔다. 근거: 그림을 로직 담당이
  즉석에서 손수 만들면(예: 코드로 도형을 그리거나 대충 합성) 품질이 떨어지고, 나중에
  DESIGN 하네스가 제대로 만들 때 이중 작업이 된다.
- **세션 안에서 직접 `git push`를 실행하지 않는다.** 근거: push는 loop.sh가 바퀴 종료
  후 대시보드 커밋과 함께 한 번에 처리한다.
- **완료한 INBOX 항목은 `- [ ]` → `- [x]`로 바꾸고 완료 날짜를 붙인다. 지우지 않는다.**
- **`docs/DESIGN.md`에 없는 기능을 임의로 지어내지 않는다.** 판단이 필요하면
  `docs/STATUS.md`의 "막힌 것/보류"에 적고 INBOX 항목은 완료 처리하지 않는다.
- **외부 서비스(API 잔액/크레딧 등) 부족으로 이번 항목이 막혔는데, `docs/STATUS.md`를
  보니 바로 이전 바퀴도 같은 이유로 이미 막혀 있었다면**, 또 조용히 다음 바퀴로 넘기지
  않는다 — 표준 출력에 정확히 `EXTERNAL_TOOL_BLOCKED: <이유를 한 줄로>`를 출력하고
  세션을 끝낸다(`loop.sh`가 이 문구를 보면 헛도는 재시도를 멈추고 사람에게 알린다).
  처음 발견했을 때는 STATUS.md에 기록만 하고 다음 바퀴에 한 번 더 기회를 준다.
- **BUILD/DESIGN 항목을 합쳐 5개 완료할 때마다, 전체를 훑는 `[QA]` 스윕 항목을 큐 끝에
  추가한다.** `docs/STATUS.md`에 "마지막 전체 스윕 이후 완료한 BUILD/DESIGN 항목 수"를
  기록해두고 세어라(없으면 0부터 시작). 5개 이상이 되면 이번 바퀴 5번(STATUS 갱신) 때
  `[QA] 전체 스윕: 메인 메뉴부터 모든 시스템을 실제로 플레이해보며 문제를 찾는다`
  형식의 새 항목을 추가하고 카운터를 0으로 리셋한다. 근거: 사람이 매번 "QA 해줘"라고
  지시하지 않아도 주기적으로 전체 점검이 이루어지게 하기 위함.

## ④ 한 바퀴 도는 순서

1. 읽기 — 위 ②의 문서를 순서대로 읽는다. INBOX.md에서 이번에 처리할 `[BUILD]` 항목
   번호(`#N`)를 확정한다.
2. 하나만 만들기 — 확정한 항목 하나만 처리한다.
3. 실행해서 눈으로 확인 — 코드를 실행해 실제로 동작하는지 확인한다. 화면에 보이는
   것이 있다면 스크린샷도 찍어서 Read 도구로 직접 본다(③에서 새 그림을 만들지 않기로
   했어도, 기존 그림/레이아웃이 이 기능과 잘 맞는지는 확인해야 한다).
4. 커밋 — 3번에서 ①을 통과하지 못했다면 커밋하지 않는다. 통과했다면 ⑤를 따른다.
5. `docs/STATUS.md` 갱신 (섹션별 규칙은 ⑤ 아래 참고) + INBOX 체크 + 위 ③의 "5개마다
   QA 스윕 추가" 카운터 갱신.

---

## ⑤ 커밋 순서 규칙 및 STATUS.md 갱신

- 검사를 통과하면, 결과 화면을 사람이 보기 "전에" 먼저 커밋한다. 작게 자주 커밋한다.
- push는 하지 않는다.
- `docs/STATUS.md`: **끝난 것/다음에 할 것 → 덮어쓴다(스냅샷)**. **막힌 것/보류 → 안
  풀린 것 유지 + 신규만 추가**. **결정 로그 → 계속 추가만, 지우지 않는다.**

### 커밋 메시지 형식

**제목**: `[INBOX #N] <이번 바퀴에서 실제로 한 일 한 줄>`

**본문**:

```
<전체 요약 1~2문장>

## 스스로 판단해서 고친 부분
- (지시와 다르게, 더 낫다고 판단해 바꾼 부분)

## 지시받지 않았지만 추가한 개선
- (하는 김에 고치거나 더한 것)

## 어려움 / 에러와 해결
- (막혔던 지점과 해결 방법)
```

## ⑥ 검사와 QA

- 화면이 있는 것을 만들었다면 실제로 실행해서 스크린샷을 찍고 직접 읽는다.
- 같은 지적이 두 번 나오면 규칙으로 올린다(③에 추가). 기계가 잴 수 있는 규칙이면
  자동 검사로 만들어 둔다.
- 깊은 "자연스러운가" 판단(그림/애니메이션 품질)은 이 하네스의 본업이 아니다 — 이상해
  보이면 고치려 하지 말고 `[DESIGN]` 항목으로 넘겨라.
