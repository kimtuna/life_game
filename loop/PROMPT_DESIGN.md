## ③ 규칙과 근거

- **어떤 도구를 쓸지는 DESIGN.md "그래픽 파이프라인"의 구분을 따른다**: 캐릭터/동물
  애니메이션(걷기, 도구 들기/사용 등)은 **SpriteCook**(`SPRITECOOK_API_KEY`)을 우선
  쓴다. 정적 오브젝트(도구 아이콘, 나무, 돌 등)는 PixelLab/SpriteCook 아무거나 쓰거나,
  파이썬 절차적 생성을 시도해볼 수 있다(단, ①을 통과 못 하면 AI 생성으로 다시 만든다).
  **PixelLab은 잔액이 $0일 수 있다 — 먼저 잔액/크레딧을 확인하고, 안 되면 SpriteCook으로
  전환할 것.** SpriteCook도 무료 크레딧만 있으니 계획 없이 여러 번 시도해서 낭비하지 말 것.
- **두 도구 모두 잔액/크레딧이 부족해서 이번 항목을 진행할 수 없다면, 무작정 "확인만
  하고 다음 바퀴로 넘기기"를 반복하지 않는다.** 절차:
  1. **처음** 이 상태를 발견했다면 — `docs/STATUS.md`에 정확한 수치(잔액, 필요한 최소
     비용)를 기록하고, 이번 바퀴는 조용히 끝낸다(다음 바퀴에게 한 번의 기회를 준다 —
     그새 충전됐을 수 있으니). INBOX 항목은 미완료로 둔다.
  2. **`docs/STATUS.md`를 보니 바로 이전 바퀴도 같은 도구·같은(또는 더 나쁜) 잔액으로
     이미 이 사실을 기록해뒀다면** — 즉 이미 한 번 확인된 반복이라면, 세 번째 바퀴를
     기다리지 말고 **표준 출력에 정확히 아래 형식으로 한 줄을 출력한 뒤 세션을
     끝낸다** (이게 있어야 `loop.sh`가 헛도는 재시도를 멈추고 사람에게 알린다):
     `EXTERNAL_TOOL_BLOCKED: <도구 이름과 부족한 잔액/크레딧을 한 줄로>`
     예: `EXTERNAL_TOOL_BLOCKED: SpriteCook 8크레딧(최소 20 필요)/PixelLab $0, 둘 다 생성 불가`
  - 근거: 예전에 이 판단 없이 매 바퀴 "재확인만" 하도록 뒀더니, 잔액이 전혀 바뀌지
    않는데도 세션이 계속 새로 열려 실질적 진전 없이 사용량만 소모됐다.
- **무엇을 만들기 전에, 선택한 도구가 이 문제를 이미 푸는 기능이 있는지부터 조사한다.**
  API 문서를 먼저 확인하고(필요하면 `curl`로 엔드포인트 목록을 조회), 손으로 합성/편집
  하는 우회법은 **공식 기능으로 안 될 때만** 쓴다. 근거: 과거에 PixelLab의
  `animate-character`/`animate-with-skeleton`/`estimate-skeleton` 같은 애니메이션
  전용 기능이 있었는데도 모르고 PIL로 손수 합성+인페인트하는 우회법을 발명해서 썼다가,
  그 결과물이 계속 부자연스럽다는 지적을 반복해서 받았다. 캐릭터가 걷거나 도구를
  사용하는 모션은 SpriteCook의 캐릭터 애니메이션 기능을 우선 시도할 것.
- **여러 색상 × 여러 방향 × 여러 모션을 한 항목에서 다 만들지 않는다.** 기준 색상
  1개(보통 green)로 필요한 방향·모션 전체를 완성해서 품질 검증까지 끝내는 항목,
  그다음 나머지 색상으로 확장하는 항목 — 최소 두 항목으로 쪼갠다(이미 DESIGN.md
  "그래픽 파이프라인"에 있는 규칙). 근거: 한 번에 다 만들려다 예산/시간 초과로 커밋
  전에 죽는 일이 여러 번 있었다.
- **완성된 자산은 반드시 실제 게임 렌더링(헤드리스 포함)으로 스크린샷을 찍어서 Read
  도구로 직접 본다.** 생성된 PNG를 확대해서만 보는 것으로 끝내지 말고, 최소 기준
  색상 1개는 실제 캐릭터에 장착된 상태로 4방향 전부 확인한다.
- **세션 안에서 직접 `git push`를 실행하지 않는다.**
- **완료한 INBOX 항목은 `- [ ]` → `- [x]`로 바꾸고 완료 날짜를 붙인다.**
- **BUILD/DESIGN 항목을 합쳐 5개 완료할 때마다 `[QA]` 전체 스윕 항목을 큐에 추가한다**
  (`PROMPT_BUILD.md` ③과 동일한 규칙 — 카운터는 `docs/STATUS.md`에 공유해서 기록).

## ④ 한 바퀴 도는 순서

1. 읽기 — 위 ②. 이번에 처리할 `[DESIGN]` 항목 번호(`#N`)를 확정한다.
2. **조사** — 이 항목이 필요로 하는 걸 PixelLab의 어떤 기능으로 만들 수 있는지 먼저
   확인한다(API 조사, 또는 STATUS.md에 이미 기록된 성공 사례 재사용).
3. 기준 색상 1개로 시도 — 여러 색상이 필요하면 1개만 먼저 끝까지 만든다.
4. 실행해서 눈으로 확인 — 실제 게임에 장착한 상태로 스크린샷을 찍고 Read로 직접
   본다. ①의 합격 기준을 스스로 판정한다.
5. 커밋 — 통과 못 하면 커밋하지 않고 STATUS.md에 이유/시도한 것을 남긴다. 통과하면
   ⑤ 형식대로 커밋한다.
6. `docs/STATUS.md` 갱신(섹션별 규칙은 아래 ⑤) + INBOX 체크 + QA 스윕 카운터 갱신.

## ⑤ 커밋 순서 규칙 및 STATUS.md 갱신

- 검사를 통과하면 바로 커밋한다. 작게 자주 커밋한다. push는 하지 않는다.
- `docs/STATUS.md`: **끝난 것/다음에 할 것 → 덮어쓴다**. **막힌 것/보류 → 유지+신규
  추가**. **결정 로그 → 계속 추가만**. 이번 바퀴에 PixelLab 사용법에서 새로 알게 된
  것(성공한 파라미터, 실패한 시도, 우회법)은 반드시 "헤드리스 CLI 검증" 절이나 결정
  로그에 남긴다 — 다음 DESIGN 바퀴가 같은 삽질을 반복하지 않도록.
