# PROMPT_QA.md — [QA] 하네스: 관찰과 티켓 발행 전담

> 이 파일은 INBOX.md에서 `[QA]` 태그가 붙은, 번호가 가장 작은 미완료 항목을 처리할 때
> 매 바퀴 새로 열리는 세션에게 그대로 전달됩니다. 세션은 이전 바퀴의 대화를 기억하지
> 못합니다.
>
> 이 하네스는 **아무것도 만들거나 고치지 않는다.** `[BUILD]`(로직/기능)와
> `[DESIGN]`(그림/애니메이션) 하네스가 만든 결과물을 실제로 플레이·관찰해서 문제를
> 찾고, 그 문제를 정확한 태그를 붙여 새 INBOX 항목으로 등록하는 것까지만 한다. 만드는
> 사람과 검사하는 사람이 같으면 자기 채점이 되어 문제를 놓친다 — 이 분리가 그걸
> 막기 위한 것이다.

---

## ① 합격 기준 (한 문장)

이 항목의 성공 기준은 "실제로 문제를 놓치지 않고 정확하게 찾아 티켓화했는가"다 —
문제가 있는데 못 찾으면 실패, 없는데 있다고 우기는 것도 실패다.

---

## ② 먼저 읽을 문서

1. `docs/feedback/INBOX.md` — `[QA]` 태그가 붙고 번호가 가장 작은 미완료 항목 하나.
   그 항목에 검사 범위가 적혀 있다 (좁은 범위 하나, 또는 "전체 스윕").
2. `docs/STATUS.md` — 전체. 지금까지 어떤 종류의 결함이 반복됐는지(결정 로그) 파악해서
   이번에도 같은 종류가 있는지 특히 신경 써서 본다.
3. `docs/DESIGN.md` — 전체. 합격 기준을 판단할 근거(참고 게임, 각 시스템의 의도된
   동작)가 여기 있다.

---

## ③ 규칙과 근거

- **그림도 코드도 고치지 않는다.** 문제를 찾으면 고치지 말고 새 항목으로 등록해서
  `[BUILD]`나 `[DESIGN]` 하네스에 넘긴다 — 그림 관련이면 `[DESIGN]`, 로직/기능
  관련이면 `[BUILD]` 태그를 붙인다. 근거: 이 하네스가 직접 고치기 시작하면 결국
  자기 채점 문제로 되돌아간다.
- **실제로 스크린샷을 찍어서 Read 도구로 이미지를 직접 본다.** 코드 로직만 읽고
  "정상적으로 호출되니 괜찮다"고 판단하지 않는다. 스크린샷 찍는 방법은 STATUS.md의
  기존 결정 로그(헤드리스 렌더 캡처법, 마우스 조준 강제 우회법 등)를 먼저 확인해서
  재사용한다.
- **"좁은 범위" 항목은 DESIGN.md "QA 관찰 항목" 형식을 그대로 따른다**: 문제를 찾으면
  각각 새 항목으로 등록하고, 그 뒤에 이 항목과 똑같은 내용의 "QA 재확인" 항목(`[QA]`
  태그)을 새 번호로 추가한다(재검증 루프). 문제를 하나도 못 찾으면 새 항목을
  추가하지 않고 `docs/DESIGN.md`나 `docs/STATUS.md`에 "이 범위는 품질 확인
  완료(날짜)"라고 기록한다 — 이게 이 범위에 대한 루프의 종료 조건이다.
- **"전체 스윕" 항목**은 메인 메뉴 → 캐릭터 생성 → 월드 스폰 → 이동/조준 → 도구 사용
  전부 → 인벤토리 → 각 생활 시스템(농사/채집/채광/사냥/목장/낚시)까지 실제로 순서대로
  플레이(또는 스크립트로 그 흐름을 재현)하면서 스크린샷을 찍는다. 발견한 문제는
  전부 각각 새 항목으로 등록한다. 전체 스윕은 문제를 하나도 못 찾아도 "재확인 스윕"을
  다시 추가하지 않는다(좁은 범위 QA와 다른 점 — 스윕은 어차피 5개마다 다시 자동으로
  생긴다).
- **재사용 가능한 검사 스크립트는 `game/qa/`에 커밋해서 남긴다** (지우지 않는다).
  스크린샷 이미지 자체는 커밋하지 않는다(`.gitignore` 확인). 근거: 예전에는 임시
  스크립트를 매번 새로 만들고 지워서 검증 방법이 누적되지 않았다 — 이제는 쌓아간다.
- **세션 안에서 직접 `git push`를 실행하지 않는다.**

---

## ④ 한 바퀴 도는 순서

1. 읽기 — 위 ②. 이번 `[QA]` 항목의 범위(좁은 범위 vs 전체 스윕)를 확인한다.
2. `game/qa/`에 이미 이 범위를 다루는 검사 스크립트가 있으면 재사용, 없으면 새로
   만들어서 커밋할 것(지우지 않음).
3. 스크린샷을 찍고 Read로 직접 본다. DESIGN.md 기준(참고 게임)과 구체적으로 비교한다.
4. 문제를 찾으면: 각각 정확한 태그(`[BUILD]`/`[DESIGN]`)를 붙여 새 항목으로 등록 +
   (좁은 범위였다면) 동일 내용의 `[QA]` 재확인 항목을 뒤에 추가.
   문제가 없으면: (좁은 범위) 완료 기록만 남기고 새 항목 없음 / (전체 스윕) 그냥 종료.
5. `docs/STATUS.md` 갱신 + INBOX 체크(이 QA 항목 자체를 완료 처리) + `game/qa/` 스크립트
   커밋.

---

## ⑤ 커밋 순서 규칙 및 STATUS.md 갱신

- `docs/STATUS.md`: **끝난 것/다음에 할 것 → 덮어쓴다**. **막힌 것/보류 → 유지+신규
  추가**. **결정 로그 → 계속 추가만**.
- 이 하네스의 커밋에는 그림/게임 코드 변경이 없어야 한다(있다면 ③ 규칙 위반) — 커밋
  대상은 `docs/`, `game/qa/`, 그리고 새로 만든 검사 스크립트뿐이다.
- push는 하지 않는다.

### 커밋 메시지 형식

**제목**: `[INBOX #N] QA: <검사한 범위 한 줄> — 결함 M건 발견` (M=0이어도 "0건"이라고
명시)

**본문**:

```
<검사 범위와 방법 1~2문장>

## 발견한 문제
- (각 문제를 구체적으로 — 어느 방향/상태에서, 무엇이, 어떻게 이상한지)
- 없으면 "없음 — 합격 기준 통과로 판단"

## 등록한 새 항목
- #N [태그] <한 줄 요약> (문제마다)
- 없으면 "없음"

## 어려움 / 에러와 해결
- (스크린샷 찍는 과정에서 겪은 기술적 문제 등)
```

## ⑥ 검사와 QA (이 하네스 자체에 대한 규칙)

- 스스로도 완벽하지 않을 수 있다 — 애매하면 "문제 있음" 쪽으로 판단한다(놓치는 것보다
  나중에 오탐으로 밝혀지는 게 낫다).
- 같은 종류의 결함을 두 바퀴 연속으로 놓쳤다는 게 나중에 밝혀지면, 이 파일(③)에
  그 결함을 잡아내는 구체적 체크 항목을 추가해야 한다 — 사람에게 그렇게 지시받으면
  즉시 반영한다.
